**How the test pauses a projection** (worth a sentence): it opens a transaction and runs `SELECT
last_offset FROM read_models.projection_offsets WHERE projection_id = 'session-history-v1' FOR
UPDATE`. The projection's next transaction writes the history row and then waits at its offset
upsert, uncommitted; PostgreSQL's readers do not wait for row locks, so the read sees the old,
committed row (version 1). Rolling the test's transaction back lets the projection commit.


**Careful with that 179 ms (Gotcha 1):** the session history's last event there is the stop that was
held back about 5 s by the pause, yet the lag says 179 ms. `clock_timestamp()` in the offset upsert is
evaluated when the statement starts, before it waits for the row lock, so the measurement ends at the
offset write, not at the commit. In normal running nothing else locks an offset row and the commit
follows the write within a millisecond; under lock contention the number is too low. Say "from the
journal to the projection's offset write, just before its commit", or hedge. The two timestamps also
come from two clocks (the writing node's and the database's).

## 14.8 (no tag): rebuilding, for the prose

- Resetting the offsets of a projection id is shown by `ReplayTests` (all three projections replayed
  into their live tables). It changed nothing because every row's version guard skipped every event:
  the versions are the sources' sequence numbers, so they survive any replay or rebuild.
- `driver_app_feed.position` is a `bigserial` of this table: a rebuild into a new table (a new
  projection id, `driver-app-v2`) numbers its feed from 1 again, so an app holding position 1,207
  would read `after=1207` from a feed that has nothing there, or the wrong entries. Nothing in the
  sample detects a new feed epoch yet (the feed DTO has no epoch field); section 20.9 completes the
  story. Say "must", not "does".
- A driver-app rebuild asks each listing for its name again (`ListingDisplayNames`), so rebuilt cards
  carry the names of the rebuild's day, not the session's.
- The SQL read journal's live query polls every 100 ms; a rebuild from offset 0 reads in batches of
  `max-buffer-size` (500 by default, unchanged).

## Surprises and gotchas (for the writer)

1. **The lag is measured to the offset write, not the commit** (14.3; details above):
   `clock_timestamp()` is taken when the upsert starts, before it waits for a lock. Measured 179 ms
   for an event a lock had held back about 5 s.
2. **A union value is not its case:** `read.ShouldBeOfType<CaughtUp<Row>>()` failed ("read should be
   of type"); `read.Value.ShouldBeOfType<CaughtUp<Row>>()` works, as elsewhere in the sample.
3. **`timestamptz` keeps microseconds, .NET ticks are 100 ns:** the feed's JSON (serialized from the
   C# card) and the card read back from the table differed in `StartedAt` by a few ticks, and the
   records were unequal although they printed the same. `DriverAppCard` now keeps its times in UTC to
   the microsecond (`Stored`).
4. **The in-memory read journal numbers a tag's events from 0, and reads `Offset.Sequence(0)` as "from
   the start".** Probed: `CurrentEventsByTag(tag, NoOffset)` gave `Sequence:0, Sequence:1`;
   `CurrentEventsByTag(tag, Sequence(1))` gave nothing; a live `EventsByTag(tag, Sequence(0))` gave
   both. Akka.Persistence.Sql's offsets are the journal's global ordering, from 1. So the runner's
   "stored 0 = nothing handled yet" re-delivers the first event after a restart on the in-memory
   journal; an idempotent projection does not mind. The first version of `InMemoryRunnerTests`
   expected offsets `[2, 3, 4]` and timed out ("delivery-log/charging did not reach offset 3.").
5. **`EventEnvelope.Timestamp` is the writing node's `DateTime.UtcNow.Ticks`, not Unix
   milliseconds** (probed: envelope `639294768331124129`, `DateTime.UtcNow.Ticks`
   `639294768343518766`, Unix ms `1793880034351`), and not the actor's `TimeProvider`. The in-memory
   journal stamps ticks too.
6. **The state-sourced listing's events never reach a projection.** The first version of 14.6 read
   `ChargePointListingRevised` from the `charging` tag; `DriverAppTests` timed out waiting for the
   name. `StateSourcedDeciderActor` deletes every event up to and including the snapshot's as soon as
   the snapshot is saved (section 11.7), and Akka.Persistence.Sql's tag query skips deleted rows, so
   the 100 ms poll never sees one. Chapter 11 says so in the book ("a read model that needs a display
   name, such as the driver app's in section 14.6, must take it from the listing's current view, not
   from its events"), so the projection asks the listing instead. A shell change that kept the latest
   event was tried and reverted (it would have contradicted the published Chapter 11 and its journal
   tour).
7. **`Match` is ambiguous again** in `Ohmline.Charging.ReadModels` (the Chapter 13 gotcha 11, now in
   src): `ConnectorId.TryCreate(...).Match<ChargePointId?>(...)` failed with `error CS1929:
   'Result<ConnectorId, ValidationError>' does not contain a definition for 'Match' and the best
   extension method overload 'TaskOptionAsyncExtensions.Match<ChargePointId?>(...)' requires a receiver
   of type 'Task<LanguageExt.Option<...>>'` (LanguageExt arrives transitively). The projection switches
   on the union's cases instead.
8. **`ToListAsync` is ambiguous in `Ohmline.IntegrationTests`:** `error CS0121: The call is
   ambiguous between ... System.Linq.Async 6.0.1 ... and ... System.Linq.AsyncEnumerable` (the BCL's
   own, .NET 10+). The test collects with `await foreach`. The Api project, which has no
   System.Linq.Async, uses the BCL's `Select`/`Prepend` on `IAsyncEnumerable` without trouble.
9. **`Tell` with one argument needs `using Akka.Actor;`** in a test file (`error CS7036: There is no
   argument given that corresponds to the required parameter 'sender' of 'ICanTell.Tell(object,
   IActorRef)'`).
10. **Testing a polling loop on a fake clock:** advancing the clock after each read raced with the
    helper; the test clock overrides `CreateTimer` to count waits (`WaitingClock`, a `SemaphoreSlim`),
    and the test advances only once the helper is waiting.
11. **Every subscriber hears every session.** The topic `session-summaries` carries all sessions'
    summaries; each per-request subscriber and the bridge filter or route by id. Fine for the sample;

## Deviations from the outline (with reasons)

- **14.4:** `SessionSummaryChanged` lives in `Ohmline.Charging.Contracts/Live`, as a `closed record
  LiveUpdate` with a manifest, because it crosses nodes on DistributedPubSub (architecture §5.1, §7)
  and both `ReadModels` (publisher) and `Api` (subscriber) need it. The projection does not publish
  itself: `IProjectionHandler.HandleAsync` returns `ImmutableArray<LiveUpdate>` and the runner
  publishes after its commit, because only the runner knows when the commit happened.
  `Ohmline.Charging.Api` references `Akka.Cluster.Hosting` (for `DistributedPubSub`, `Subscribe`); the
  architecture's §4 table lists only `Akka.Hosting` for `*.Api`. Please confirm or amend §4.
  `GET /sessions/{id}/events` also answers 204 once the browser has seen the end, and ends the stream
  after `ended`.
- **14.5:** the bridge is started by `AddChargingLiveUpdates()` (Charging.Api) from the node's Akka
  chain; the hub is mapped on every node, also without PostgreSQL.
- **14.6:** **tags are `charging-session` only, not also `charging`.** The listing's events are
  deleted as soon as its snapshot is saved (section 11.7), so the `charging` tag never delivers a
  display name, and the published Chapter 11 already says the driver app takes the name from the
  listing's current view. The projection therefore asks the listing actor (`IChargePointNames`,
  `ListingDisplayNames`) when it makes a card, through a new default member
  `IProjectionHandler.RunningIn(ActorSystem)` that the daemon calls. `driver_app_cards` has one more
  column than listed, `meter_start_wh` (as in `session_history`, to compute energy from each meter
  value), plus a unique index on `session_id` (later events carry only the session id). The feed
  endpoint's `limit` defaults to 100, at most 500; `/cards` returns the active card, up to 10 recent
  ones and the feed position, read in one snapshot. The hub's `driverCardChanged` carries a feed entry
  (`Position` and `Card`).
- **14.7:** the "fast ProjectionRunner test over the in-memory read journal" still needs PostgreSQL,
  because the runner writes rows and offset in one `NpgsqlTransaction`; it is fast in that it needs no
  journal file, no cluster and no SQL polling (645 ms), but it carries the `Integration` trait. The
  container-free tests are `ProjectionRulesTests`, which run every projection's pure rules over the
  in-memory journal's events. "Pure handler tests for every projection" are `SessionHistoryRowTests`
  and `ConnectorStatusChangeTests` (Chapter 13), `DriverAppCardTests` (14.6) and
  `ProjectionRulesTests` (14.7).
