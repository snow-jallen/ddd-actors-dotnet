## ch19-s03: Commands you can send twice

**Pure core (`Ohmline.Charging.Domain/Journeys`):**

- `JourneyTerms` gains `CommandId StartedBy` (last parameter; from `JourneyStarted.CommandId`,
  which was already stored).
- `JourneyAnswer.cs` (new, **quote whole**): `public union JourneyAnswer(AcceptedNow,
  AcceptedAsBefore, Refused);` with `Refused(string Code, string Message)`.
- `JourneyRefusals.cs`: `JourneyExists = "journey-exists"`.
- `JourneyStep` gains `public JourneyAnswer Answer { get; init; } = new AcceptedNow();`.
- `ChargingJourney.Next`: first lines `if (input.Value is StartCharging start && state.Terms is {
  } terms) { return StartedAlready(state, start, terms); }`; `StartedAlready` (**quote with its
  summary**): no events, no effects, `Answer = start.CommandId ==
  terms.StartedBy ? new AcceptedAsBefore() : new Refused(JourneyRefusals.JourneyExists, $"Journey
  {terms.JourneyId} was started by another command.")`. Covers every started state, abandoned too.
- Shell `ChargingJourneyActor`: `_startedVersion = LastSequenceNr` in `Remember` (stored or
  replayed `JourneyStarted`), and `Done` replies `AnswerTo(step)`:
  `AcceptedNow => new CommandAccepted(LastSequenceNr)`, `AcceptedAsBefore => new
  CommandAccepted(_startedVersion)`, `Refused refused => new CommandRejected(refused.Code,
  refused.Message)`, `null => throw`. Before s03, a repeated start got
  `CommandAccepted(LastSequenceNr)`, the current version, not the original one.

**Edge:** each `/app/v1` command takes `[FromHeader(Name = "Idempotency-Key")] string?
idempotencyKey` and calls `KeyMismatch` first: a header that is not the body's `commandId` → **400**
`idempotency-key-mismatch` (`Problems.BadRequest`), "The request contradicts itself." The body's
`CommandId` goes into the command unchanged (it did at s02 already). `RejectionCodes` gains
`journey-exists` and `idempotency-key-mismatch` (append-only, 10 codes).

**Docs:** `docs/idempotency-contract.md` (new): why commands are sent twice, rules for the app (5)
and the server (3), a table of how each aggregate remembers (charge point and session: the
256-id window of section 12.6; journey: `JourneyTerms.StartedBy`, for the journey's life), **why
256 is longer than 24 hours** (a busy charge point accepts about a hundred commands a day; a
session accepts none after its stop) and what happens if it is not (decided again: a reservation
likely refused, a stop "already ended"), and commutative commands versus a hypothetical
`expectedVersion` + `stale` (not implemented: Ohmline has no such command). `RecentCommands`'
`DefaultCapacity` summary now mentions the app's 24 hours. The client README links the contract.

**Tests:** `Charging.Domain.Tests/Journeys/SendTwiceTests` (8 cases: steps taken 1, 2, 3, 5, 6);
`Charging.Actors.Tests/Sqlite/JourneySentTwiceTests` (**quote the first test**): the real
SQLite journal through `SqliteNode`; the journey actor started directly, so the test decides when
it stops; `Given_the_same_start_three_times_and_a_restart_then_one_journey_started` (replies
`CommandAccepted(1)` three times; `JournalTourQueries` finds one row,
`charging.journey-started.v1`) and `Given_a_started_journey_when_another_command_starts_it_then_
journey_exists`; `Charging.Api.Tests` (`..._idempotency_key_that_is_the_command_id_...`,
`..._names_another_command_then_400_...`, `..._409_journey_exists`);
`IntegrationTests/RestartSurvivalTests.Given_a_stop_sent_again_after_a_restart_then_the_same_
version` (start → v1; `POST /app/v1/sessions/{id}/stop` → `{commandId, version: 2}`; node

## Surprises and gotchas (for the writer)

1. **C# 15 extension members and explicit type arguments.** `Currency.TryCreate(...)
   .Bind<Currency>(...)` failed with `error CS1061: 'Result<Currency, ValidationError>' does not
   contain a definition for 'Bind'`: the extension block's own type parameters (`T`, `E`) count
   too. The lambda got an explicit return type instead: `Bind(Result<Currency, ValidationError>
   (currency) => ...)` (`DriverAppCommands.PaidIn`).
2. **The minimal API binds request DTOs through the context.** `ConfigureHttpJsonOptions` with
   `TypeInfoResolverChain.Insert(0, ChargingClientJsonContext.Default)`: the server reads and
   writes the client DTOs with the generated code and everything else as before. The hub still
   uses its own protocol options (unchanged on the server; same camelCase JSON).
3. **Validation order.** A first version skipped the currency check when another field was
   invalid (`if (fields.AreValid && ...)`), and the 422 named only some fields; the checks are now
   `Result`s read with `fields.Read`, so every field is reported (test
   `Given_fields_that_are_not_valid_then_422_with_the_code_and_each_field`).
4. **`Known.Command` is a property** in `Charging.Actors.Tests` (a new v7 id per call), so
   `TheJourney.Start()` is a new command each time: `JourneySentTwiceTests` keeps one `start`
   instance for "the same command".
5. **MAUI's global usings include `Microsoft.Maui.Networking`**, so the app's own
   `IConnectivity` is ambiguous in the head: `error CS0104: 'IConnectivity' is an ambiguous
   reference between 'Microsoft.Maui.Networking.IConnectivity' and
   'Ohmline.Mobile.Core.Platform.IConnectivity'`. `MauiProgram` aliases it;
   `MauiConnectivity` uses `using MauiNetwork = Microsoft.Maui.Networking;`.
6. **No `Microsoft.Extensions.Configuration.Json` in MAUI's package closure** (the template's
   `project.assets.json` has Configuration, DependencyInjection, Logging, Logging.Debug only).
   Rather than add a package, `AppSettings.Load` reads the embedded file with `JsonDocument`.
7. **MAUI 11's XAML source generator** (rc.2): `required` or `init` properties set from XAML fail
   with `error MAUIX2005: '...ScreenStateTemplates.Loading' has the 'required' keyword. Support
   for this in XAML is limited at the moment, avoid using it.` and `error CS8852: Init-only
   property ... can only be assigned in an object initializer` in the generated
   `*.xaml.xsg.cs`. The template properties are `{ get; set; } = null!;` with a remark.
   **And a real bug, not fixed in the tags (errata):** after `AppShell.xaml` changes, the first
   build of the head through a warm compiler server fails with `error CS0200: Property or indexer
   'ShellItem.Items' cannot be assigned to -- it is read only` in `AppShell.xaml.uc.xsg.cs`, the
   `UpdateComponent` of XAML Incremental Hot Reload (on by default in Debug in .NET 11). Deleting
   `obj/` does not help; `dotnet build-server shutdown`, `-p:UseSharedCompilation=false` or
   `-p:EnableMauiIncrementalHotReload=false` do. It is why `verify-tags.sh` failed s05 and s07
   (see Verification). If the prose has the reader step through the tags and build the head,
   add a `Version note`: "If the head fails with CS0200 in `AppShell.xaml.uc.xsg.cs` after you
   check out another tag, run `dotnet build-server shutdown` and build again: a bug in MAUI
   11 rc.2's XAML hot reload generator."
8. **Overlapping refreshes.** `SessionCardViewModel` refreshes on pushes and on dispatcher
   events, fire-and-forget; without the `SemaphoreSlim`, a refresh that read before a push could
   finish after one that read after it and put the stale overlay back. One at a time, each
   reading anew, the last to finish is the latest.
9. **`Start()` does not nudge.** An early version did, and `Start(); FlushAsync()` then drained
   twice, sending a transiently failed command a second time at once; the head now calls
   `Start(); Nudge();` and the tests `Start(); FlushAsync();`.
10. **The test server does not propagate `traceparent`.** `WebApplicationFactory`'s in-memory
    handler is not `SocketsHttpHandler`, so it creates no HTTP client span and injects nothing;
    `TapToJournalTraceTests` adds a `DelegatingHandler` that does what `HttpClient`'s own handler
    does on a phone. Whether the Android handler injects `traceparent` was not run on a device:
    hedge ("HttpClient's handler injects the current span's traceparent, as on any .NET
    platform").
11. **The node's SDK records the app's spans in the same process** (`AddSource("Ohmline.*")`),
    which is why one in-memory exporter shows the whole trace. On a phone they go to the app's
    own exporter, if any.
12. **`DriverCardChanged`'s internal golden file changed** (`"traceParent": null` added). It is a
    `LiveUpdate` on DistributedPubSub, never persisted, so accepting the change is safe; a node
    of the previous build reads the new JSON (unknown member ignored) and the new build reads the
    old (missing → null). Say "additive", not "a new manifest version".
13. **`OutboxDispatcher`'s `Signal` is a nested private union** of two nested private records;
    `switch` statements over `SendOutcome` use `case SendAccepted accepted:` and `case null:`.
14. **Unrelated flakes seen in the full runs**, both already in the errata: `LinkTests`
    (ch17-s07) at s07, the `Ch02.Hosted` shutdown race at s08; each tag's rerun was green.

## Deviations from the outline (with reasons)

- **19.2:** `ProblemDto` added to the client contracts (the app must read the 409/422 problem's
  `code` without ASP.NET Core's `ProblemDetails` type). `DriverSessionCards` and `DriverFeedPage`
  added (the responses of `/cards` and `/feed` were DTOs in `App/Dtos` too). The unknown-connector
  answer on `/app/v1/journeys` is 422 `unknown-connector`, not 404, so that every refusal the app
  sees carries a code. Charging.ReadModels references Client.Contracts (allowed by §4) to write the
  feed payload in the published language. `ConnectorPlacement` was extracted so the two start
  endpoints share the charge point lookup.
- **19.3:** the journey's test uses the existing `SqliteNode` harness (Akka.Hosting on a SQLite
  file, as `TwoIncarnationsTests`) and creates the journey actor directly, rather than
  `Akka.Hosting.TestKit`: the restart is "a journey restart", which needs the test to stop the
  entity, and a sharded journey with remember-entities is restarted by its shard. The same
  journal, serializer and recovery path are exercised.
- **19.5:** `SpendCap` is a single-currency value object (`Currency = "USD"`, the server's
  `HoldCurrency`); `DriverToken` (the driver's token in the app) was needed and is filled from
  `appsettings.json`. Rendering goes through a small `StateView` + `IStateTemplates` in the head,
  because a `DataTemplateSelector` cannot both switch over the union and bind to the case.
- **19.6:** the `SendOutcome` cases are named `SendAccepted`, `SendRejected`,
  `SendTransientFailure` (as in `research/mobile.md`): `Accepted` and `Rejected` are already
  `CommandStatus` cases in the same library. The dispatcher, not the head, nudges on
  `IConnectivity.ConnectivityChanged` (subscribed while started), so it is tested in
  Mobile.Core; the head's part is the window lifecycle. `FlushAsync` is an addition (deterministic
  tests). The stored kind/route mapping (`OutboxKinds`, `HttpCommandSender.RouteOf`) was needed
  to send stored payloads.
- **19.7:** a session page and a stop command were added to the app so that the overlay has a
  command whose accepted version is the card's (the start's version is the journey's; the start's
  overlay goes when its session has a card). `SqliteOutbox.ReadSinceAsync` added.
- **19.8:** **`Aspire.Hosting.Maui` was not verified**, so the AppHost is unchanged and
  `docs/observability.md` gained the section instead, as the outline allows: no emulator or
  system image is installed, the dev tunnel CLI is not available, and the package is a preview.
  The OTLP exporter uses HTTP/protobuf with a full `/v1/traces` URL from `Ohmline:OtlpEndpoint`
  (the phone has no environment variables). Release builds sample 1 in 10 (parent-based).
  `SqliteOutbox.EnqueuedByThisProcess` is how "the process restarted since the tap" is known
  (the outline's columns have no process id).
