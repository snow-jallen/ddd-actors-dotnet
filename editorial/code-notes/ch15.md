## ch15-s01: Saga or process manager? Choreography first

**Files:**

- `src/Ohmline.SharedKernel/Identity/GuidV7.cs`: new `public static Guid Derive(Guid origin, string
  purpose)` (summary from line 14, method lines 20-39). It keeps the origin's 48-bit timestamp (bytes 0-5, big-endian), fills the
  other bytes from `SHA256.HashData(Encoding.UTF8.GetBytes($"{origin:D}/{purpose}"))`, and sets the
  version nibble to 7 and the RFC 9562 variant bits. Summary: "The id of something that follows from
  origin for one purpose: the same pair gives the same id every time, and different pairs give
  different ids. It keeps the origin's time, so it still sorts where the origin does..."
- `src/Ohmline.SharedKernel/Identity/CommandId.cs`: `public static CommandId Derive(CommandId cause,
  string purpose) => new(GuidV7.Derive(cause.Value, purpose));` with the summary "The id of a command
  that follows from another, such as the release a subscriber sends when a session ends...".
- `src/Ohmline.SharedKernel/GOVERNANCE.md`: row `| 2.8.0 | GuidV7.Derive and CommandId.Derive ... |
  15.1 |`.
- `src/Charging/Ohmline.Charging.ReadModels/Policies/SessionEndedSubscriber.cs` (**quote whole, 118
  lines**; or the class summary and remarks, `CommandsFor` and `Translate` lines 68-97, `SendAsync`
  and `AskAsync` 99-116): `public sealed class SessionEndedSubscriber(ActorSystem? system = null) :
  IProjectionHandler`, `public const string Id = "session-ended-subscriber-v1"`, tags
  `[ChargingTags.ChargingSession]`, `FailurePolicy = new RecordAndSkip(MaxRetries: 5)` (comment: "A
  release that never arrives keeps one connector's power from the others, which is bad; a subscriber
  that stops keeps every connector's power from them, which is worse."), `RunningIn(ActorSystem)`
  returns a subscriber that resolves the regions with `ActorRegistry.For(system).GetAsync<TRegion>`.
  `HandleAsync` writes no rows and returns `[]`. `public static ImmutableArray<SessionEndedCommand>
  CommandsFor(SessionEvent @event)` runs `ReleaseOnSessionEnded.React` and translates each intent:
  `ReleaseSiteAllocation` → `new ReleaseAllocation(CommandId.Derive(cause, "release-allocation"),
  ...)`, `UnlockToken` → `new UnlockFromSession(CommandId.Derive(cause, "unlock-token"), ...)`;
  `StopCharging`/`WarnOfIdleFee` → null ("Not this subscriber's"). Each command is sent with `Ask`
  (5 s); no answer throws, so the runner retries the event; a refusal is an answer.
- `.../Policies/SessionEndedCommand.cs` (10 lines, quote whole): `public union
  SessionEndedCommand(ReleaseAllocation, UnlockFromSession);` "a union of their own records, which
  share no base type" (a teaser for 15.2).
- `.../ChargingReadModelsExtensions.cs`: `new SessionEndedSubscriber()` appended to `Streams` (fifth
  stream).
- `.../Ohmline.Charging.ReadModels.csproj`: references `Ohmline.DriverAccounts.Contracts`.

**Tests:** `tests/Ohmline.Charging.ReadModels.Tests/Policies/SessionEndedSubscriberTests.cs`:

**Writer's points:** the subscriber is choreography: no state, no journey, a "whenever X then Y"
reaction that crosses two contexts. It is a projection with no table, so its offset is stored "like
any projection" (in the runner's transaction, `read_models.projection_offsets`), and its sends are
at least once; `CommandId.Derive` makes the second send the same command, so the receiving shell's
recent-command window (12.6) and the deciders' state both make it harmless.

## Surprises and gotchas (for the writer)

1. **Remember-entities and the journal.** The first version used
   `RememberEntitiesStore.Eventsourced` (remembered entities in the journal). It made the sharding
   coordinator persist an event under the persistence id
   `/system/sharding/charging-journeyCoordinator/singleton/coordinator` as soon as the region
   started, and that row took a place in the journal's global ordering, at a moment that races the
   first command. 13 existing tests that read orderings (tags offsets 1, 2, 3 in
   `ReadJournalTourTests`, `ProjectionRunnerTests`, `ProjectionFailureTests`, `JournalTourTests`) and
   `CurrentPersistenceIds` failed, e.g. `should be [1L, 2L, 3L] but was [1L, 3L, 4L]`. The default
   store (`DData` with durable keys `shard-*`) writes LMDB files to a `ddata-...` directory on each
   node's disk. The sample keeps the list in distributed data **in memory**
   (`WithShardingDistributedData(ddata => ddata.Durable.Keys = [])`): it survives a rebalance and the
   loss of a node, not the loss of every node at once. The trade-off is in the remarks of
   `JourneyShardOptions()` and is worth a sentence in 15.3.
2. **`FirstOrDefault` on a record struct.** `site.Allocations.FirstOrDefault(...) is { } allocation`
   matched the *default* `PowerAllocation` (a `readonly record struct`) when the connector had none,
   and answered a queued request with `PowerAllocated { Allocated = 0 kW }`. Caught by
   `Given_a_site_with_no_room_when_power_is_requested_then_it_is_queued`; fixed with
   `.Select(allocation => (Power?)allocation.Power).FirstOrDefault()`.
3. **`ShardOptions.DistributedData` is obsolete** in Akka.Cluster.Hosting 1.5.73: `error CS0618:
   'ShardOptions.DistributedData' is obsolete: 'This property is not being applied to the ActorSystem
   anymore. Use WithShardingDistributedData() extension method ... Since v1.5.27'`. Sharding's
   distributed data is one per role, shared by every region.
4. **`Charging` is a namespace and a state.** In any namespace under `Ohmline` other than
   `Ohmline.Charging.Domain.Journeys`, the simple name `Charging` binds to the namespace
   `Ohmline.Charging` before any `using`; tests and the view mapping alias it (`using ChargingState =
   Ohmline.Charging.Domain.Journeys.Charging;`).
5. **A union struct and `ShouldBeOfType`.** `step.State.ShouldBeOfType<Abandoned>()` fails ("should
   be of type Abandoned but was JourneyState"): the union is a struct. Use
   `step.State.Value.ShouldBeOfType<Abandoned>()`; `ShouldBe(new AwaitingHold(...))` works through the
   implicit conversion.
6. **Name clashes from `using static`.** A test fixture property named `Lock` clashed with
   `System.Threading.Lock`, and `Void` with `void` (CS0229); the fixture uses `AskForLock`,
   `VoidTheHold`, `ReleaseThePower`, `UnlockTheToken`.
7. **The reply timer and the transition table.** Rows first decided at "the minute after the step
   began" hit the one-minute `StepTimeout` and abandoned; the table now decides ten seconds into each
   step.
8. **Persist before acting, demonstrated:** with `WithJournalWrite(write => write.Fail())` the
   journey stops and the token region hears nothing
   (`Given_a_journal_that_fails_the_write_then_nobody_is_asked_anything`).
9. **TestScheduler and Ask.** In `ChargingJourneyActorTests` the ports' `Ask` timeouts also run on
   the `TestScheduler`; no test moves time while an `Ask` is pending.
10. **Akka.Delivery is in 1.5.73:** `Akka.Delivery.ProducerController`, `ConsumerController`,
    `Akka.Persistence.Delivery.EventSourcedProducerQueue`,
    `Akka.Cluster.Sharding.Delivery.ShardingProducerController`/`ShardingConsumerController` are in
    the 1.5.73 assemblies (checked in the XML docs). Not run.

## Deviations from the outline (with reasons)

1. **`NotStarted` in `JourneyState`, no `Started` state.** The outline lists `Started` first. A
   journey asks for the token lock in the same step that starts it, so a "started, nothing asked
   yet" state would hold no journey ever; the union needs an initial state instead. `JourneyStarted`
   moves `NotStarted` → `AwaitingTokenLock`.
2. **`Next(state, input, DecisionContext)`**, not `Next(state, input)`: events are stamped with the
   time and timers run from when a step began, so the time is passed in (read once by the shell),
   as for every decider. `Next` returns `JourneyStep(State, Events, Effects)`: the outline's
   "(state, effects)" plus the events the shell persists.
3. **Step events are named `TokenSecured`, `HoldSecured`, `PowerSecured`, `EnergyFlowStarted`,
   `SettlementDue`** (the outline's "StepCompleted..."). `TokenLocked` and `AllocationGranted` were
   taken: they are Driver Accounts' reply and Site Energy's event.
4. **Site Energy's replies are `PowerAllocated` and `QueuedForPower`**, not
   `AllocationGranted`/`AllocationQueued`: those names are Site Energy's domain events, and the
   budget actor uses both namespaces. The pattern follows Driver Accounts (reply `TokenLocked`, event
   `TokenLockedForSession`).
5. **`BudgetCommandRejected` and `HoldVoided` are journey inputs too**: a refused request for power
   must abandon the journey; a void's confirmation must be a case the table says "nothing" to.
6. **The journey's session is named after it** (`ChargingJourney.SessionOf(journeyId)` = the same
   Guid). The outline does not say how session events reach the journey; this gives the relay and the
   region's extractor a route with no lookup. A session no journey started reaches a journey that
   never started, which answers and passivates.
7. **`JourneySessionRelay` (projection `journey-session-relay-v1`) is new**, added in `ch15-s04`. The
   outline names no mechanism for "Charging session events" as inputs. It is a durable name; ADR 0009
   lists it (in the s06 commit). Please add it to architecture §6.
8. **The port interfaces arrive in `ch15-s03`**, with the actor that needs them to compile; `ch15-s04`
   adds the Development implementations, their registration, the relay and the autopilot tests. At
   `ch15-s03` the node maps `POST /journeys` but cannot create a journey entity (no port registered:
   the request times out with 504). Say so if 15.3 has a "Try it".
9. **The edge enriches `StartCharging`**: the request is TokenUid + ConnectorId as outlined; the
   command also carries `SiteId`, `MaxPower` (from the charge point's status) and `Hold` (from
   `ChargingApiOptions.HoldAmount`/`HoldCurrency`, 50 USD). Chapter 19's request adds a spend cap.
10. **The capture amount is `SessionTerms.CostOf(delivered)`** under the session's tariff snapshot:
    "the same figure its spend cap is checked against" (highest energy rate plus session fee), not
    the price calculator's exact price (Tariffs.Domain is not reachable from Charging.Domain). Exact
    for the sample tariffs with one energy rate; Chapter 16 prices receipts in Billing.
11. **On normal completion the journey does not release or unlock**: the s01 subscriber does that on
    `SessionEnded` (choreography beside orchestration). The journey compensates only when abandoned.
12. **Timers carry no idempotency key** ("every effect carries an IdempotencyKey"): a timer is named
    by its `JourneyTimer`, and starting it again replaces it, which is its own idempotency.
13. **Akka.Delivery not adopted** although its 1.5.73 API exists: ADR 0011 gives the reasons (a
    consumer controller in front of every site budget entity and every other sender, a second durable
    queue per journey beside its own journal). Retries under keys instead, as the outline's
    "otherwise" branch.
14. **Remember-entities store: distributed data in memory**, see Surprises 1.
15. **Reply timer and "give back what was asked for"** (s06) go beyond the outline's s06 text; they
    are what makes at-most-once delivery plus idempotency keys a complete answer.
